# ابزارهای بهره‌برداری

## `prod-verify.sh` — راستی‌آزمایی سرور تولید

پس از هر استقرار روی سرور اجرا می‌شود:

```bash
scp ops/prod-verify.sh mlz:/root/ && ssh mlz "bash /root/prod-verify.sh"
```

**فقط می‌خواند.**  عمداً هیچ ردیفی نمی‌سازد و حذف نمی‌کند.

مجموعه‌های آزمون معمولی (`untested.sh`، `restaurant.sh` و مانندشان) برای
کارشان ردیف می‌سازند و پاک می‌کنند — که روی نصب توسعه درست است و روی
دادهٔ زندهٔ مشتری نه.  آزمون کامل جای خودش روی نصب محلی است؛ اینجا فقط
سنجیده می‌شود که استقرار درست نشسته:

- مهاجرت‌ها ثبت شده‌اند
- قیدهای یکتا در محدودهٔ شرکت‌اند و سه استثنای هویتی سراسری مانده‌اند
- شمار جدول‌ها تغییر نکرده و داده سرِ جایش است
- همهٔ صفحه‌ها ۲۰۰ می‌دهند و API بدون توکن ۴۰۱

## پیش از هر مهاجرت روی تولید

```bash
ssh mlz "cd /opt/molido && docker compose -f docker-compose.yml \
  -f docker-compose.store.yml -f docker-compose.vps.yml \
  exec -T postgres pg_dump -U postgres molido_ai | gzip > /root/molido-pre-XXX-\$(date +%F-%H%M).sql.gz"
```

سپس **کامل بودنش را بسنجید**، نه فقط وجودش:

```bash
gzip -dc FILE | grep -c 'CREATE TABLE'   # باید با شمار جدول‌های دیتابیس بخواند
```

اندازهٔ فایل سنجهٔ بدی است: یک `gzip` خالی هم ۲۰ بایت است و `gzip -t`
روی آن سبز می‌دهد.  اولین پشتیبانی که امروز گرفتم دقیقاً همین بود —
سبزِ دروغین، چون `docker compose` بدون overlayها سرویس `postgres` را
نمی‌دید.

## به‌روزرسانی سرور

```bash
bash ops/update-vps.sh            # میزبان پیش‌فرض: mlz
bash ops/update-vps.sh root@1.2.3.4
```

از **دستگاهی که به سرور دسترسی دارد** اجرا می‌شود، نه روی خود سرور.

⚠️ اگر «مهلت تمام شد» گرفتید، پیش از آنکه سرور را خاموش فرض کنید،
   مسیرِ شبکه را بررسی کنید.  این سرور از بعضی شبکه‌ها فیلتر می‌شود و
   نشانه‌اش روشن است:

       مهلت تمام شد   -> فیلتر یا مسیریابی
       رد شد          -> سرویس خاموش

   سرورِ مرده سریع «connection refused» می‌دهد؛ فیلتر، سکوت.

اسکریپت هر گام را **می‌سنجد** نه اینکه به خروجیِ موفق اعتماد کند:
پشتیبان با شمارِ جدول‌ها، ساخت با زمانِ ایمیج، و کدِ تازه با یک
قابلیت که فقط در آن هست.

## `verify-restore.sh` — آزمونِ **بازیابیِ** پشتیبان

```bash
bash ops/verify-restore.sh            # میزبان پیش‌فرض: mlz
```

⚠️ پشتیبانی که بازیابی نشده، پشتیبان نیست — فقط یک فایل است.

`backup.sh` سه چیز را می‌سنجد: gzip سالم، اندازهٔ معقول، و شمارشِ
جدول‌ها.  هیچ‌کدام کافی نیست: فایلی که همهٔ `CREATE TABLE`ها را دارد
هم می‌تواند وسطِ یک `COPY` بریده باشد.  اینجا پشتیبان روی
پایگاه‌دادهٔ **موقت** واقعاً بازیابی می‌شود، سطرها با زنده مقایسه
می‌شوند، و دفترِ بازیابی‌شده باید متراز باشد.  پایگاه‌دادهٔ موقت در
هر حالت — حتی با خطا — پاک می‌شود.

## `watchdog.sh` — دیده‌بان

```bash
# روی سرور، در crontab:
*/5 * * * * /opt/molido/ops/watchdog.sh >> /var/log/molido-watchdog.log 2>&1
```

هر پنج دقیقه `/health` را می‌سنجد.  دو شکستِ پیاپی ⇒ یک بار تلاش
برای بلند کردن، و اگر نشد **یک** پیامک.  تا بازگشت ساکت می‌ماند و
موقعِ بازگشت یک پیامکِ خبرِ خوب می‌فرستد.

شمارهٔ هشدار را در `.env` بگذارید:

```
WATCHDOG_SMS_TO=09120000000
```

بدونِ آن هم کار می‌کند — فقط لاگ می‌نویسد.  کلیدِ پیامک از
`SMS_API_KEY`ِ همان `.env` خوانده می‌شود، نه از آرگومان: آرگومان در
`ps` دیده می‌شود.

ماشینِ حالتش با `backend/test/watchdog.sh` آزموده می‌شود (۱۲ سنجه،
با بدلِ پیامک و داکر) — تنها اسکریپتی که کارش وقتی همه‌چیز خراب است
شروع می‌شود، پس خودش نباید نیازموده بماند.

## مهاجرت از نرم‌افزارِ دیگر

⚠️ پشتیبانِ هلو/سپیدار/همکاران **مستقیم خوانده نمی‌شود** — و این
تصمیم است، نه کمبود.  قالبشان بسته است (اغلب SQL Server یا فایلِ
رمزشده) و نسخه‌به‌نسخه عوض می‌شود؛ کدی که بخواندشان با هر
به‌روزرسانیِ آن‌ها می‌شکند، و شکستنش وسطِ راه‌اندازیِ یک فروشگاه رخ
می‌دهد.

ولی **هر** کدامشان «خروجی اکسل» دارد.  مسیرِ مطمئن همین است:

1. از نرم‌افزارِ خودتان خروجی اکسل بگیرید و به CSV ذخیره کنید.
2. در پنل: **ورود گروهی ← از نرم‌افزار دیگر**، نوعش را انتخاب کنید.
3. پیش‌نمایش را ببینید — چند سطر تازه است، چند سطر خوانده نشد.
4. «اعمال» بزنید.

ستون‌ها از روی **نامشان** شناخته می‌شوند؛ لازم نیست فایل را دستکاری
کنید.  نیم‌فاصله و «ي/ك» عربی هم مانع نیست.

| چه چیزی | ستون‌های شناخته‌شده |
|---|---|
| کدینگ حساب | کد حساب، نام حساب، ماهیت، کد والد |
| گروه کالا | گروه، گروه والد |
| تأمین‌کننده | نام، تلفن، آدرس، ایمیل |
| کالا | (صفحهٔ ورود گروهی — کد، نام، واحد، بارکد، قیمت، موجودی) |

⚠️ **ماهیتِ حساب حدس زده نمی‌شود.**  سطری که ماهیتش شناخته نشود رد
می‌شود و در فهرستِ «سطرهای خوانده‌نشده» با شمارهٔ خط می‌آید.  علتش
این است که حسابِ با ماهیتِ غلط در ترازنامه سمتِ اشتباه می‌نشیند و
ترازِ آزمایشی **همچنان صفر می‌ماند** — یعنی هیچ سنجه‌ای نمی‌گیردش.
پذیرفته: دارایی، بدهی، سرمایه، درآمد، هزینه (و معادل‌های انگلیسی).

⚠️ حسابی که فرزند دارد خودکار **غیرسندپذیر** می‌شود، وگرنه می‌شد سند
را به «دارایی‌های جاری» زد به‌جای «صندوق» و گزارشِ معین برای همیشه
ناقص می‌ماند.

بازیابی **افزایشی** است: آنچه از قبل هست دست نمی‌خورد.  می‌توانید
همان فایل را دوباره بدهید — چیزی تکراری نمی‌شود.

## زیردامنهٔ جدا برای هر محصول

```bash
bash ops/set-subdomains.sh shop.molido.ir cafe.molido.ir
```

پیش از آن، این دو رکورد را در پنلِ دامنه بسازید — هر دو به آی‌پیِ
سرور:

```
A   shop    194.5.176.140
A   cafe    194.5.176.140
```

اسکریپت **پیش از هر تغییری** DNS را با دو حل‌کنندهٔ عمومی می‌سنجد و
اگر آماده نباشد هیچ کاری نمی‌کند.  علتش این است که Caddy با دیدنِ
دامنه دیگر `tls internal` نمی‌زند؛ رکوردِ غلط یعنی گواهی صادر نشود و
سایت **از دسترس خارج** شود — نه یک هشدارِ مرورگر.

### چه چیزی زیرِ کار عوض می‌شود

فروشگاه و رستوران دو پروژهٔ Docker جدا با شبکه‌های جدا هستند؛ Caddy
در یکی می‌نشیند و راهی به دیگری ندارد.  پس یک شبکهٔ سومِ مشترک
(`molido_edge`) ساخته می‌شود و هر دو به آن وصل می‌شوند.

⚠️ هر دو پروژه سرویسی به نامِ `backend` دارند.  روی شبکهٔ مشترک،
نامِ `backend` به **یکی از دو** کانتینر حل می‌شود و کدام‌یک به ترتیبِ
بالا آمدن بستگی دارد — یعنی زیردامنهٔ فروشگاه گاهی دادهٔ رستوران را
نشان می‌دهد، بی‌آنکه چیزی خطا بدهد.  به همین دلیل نامِ مستعارِ صریح
(`store-backend`، `resto-backend`) اجباری است و Caddy فقط با همان‌ها
کار می‌کند.

### دامی که یک بار سایت را خواباند

`{$VAR} { ... }` وقتی متغیر تهی باشد «بلوکِ بدون نشانی» می‌شود و
Caddy کلِ فایل را رد می‌کند.  و نکتهٔ ظریفش:

| حالت | نتیجه |
|---|---|
| متغیر تعریف‌نشده | پیش‌فرضِ `{$VAR:x}` اعمال می‌شود ✓ |
| متغیر **تهی** (`VAR=`) | پیکربندی باطل، سایت پایین ✗ |
| مقدارِ `.invalid` | معتبر ✓ |

و `docker compose` با الگوی رایجِ `${VAR:-}` دقیقاً حالتِ وسط را
می‌سازد.  پس در `docker-compose.edge-caddy.yml` پیش‌فرض‌ها
`store.invalid` و `resto.invalid`اند، نه رشتهٔ خالی.
`backend/test/caddy.sh` هر سه حالت را می‌سنجد.

### گواهیِ معتبر

⚠️ روی این سرور Let's Encrypt با چالشِ معمول **کار نمی‌کند**: سرور
از داخل ایران در دسترس است و از بیرون نه، و سرورهای اعتبارسنجی
بیرون‌اند.  زیردامنه هم این را عوض نمی‌کند.

تنها راه چالشِ **DNS-01** است — اتصالِ ورودی نمی‌خواهد.  لازمه‌اش
ارائه‌دهندهٔ DNS با API (Cloudflare رایگان کافی است) و تصویرِ Caddy
با افزونهٔ `caddy-dns/cloudflare`.

تا آن وقت زیردامنه‌ها با **گواهیِ خودامضا** کار می‌کنند
(`MOLIDO_TLS_SUB=tls internal`، پیش‌فرضِ compose) و مرورگر یک بار
هشدار می‌دهد.

⚠️ **این متغیر را خالی نکنید تا وقتی DNS-01 راه نیفتاده.**

بلوکِ بدونِ دستورِ tls سراغ Let's Encrypt می‌رود، چالش شکست می‌خورد،
و آن زیردامنه **هیچ گواهی‌ای نمی‌گیرد** — یعنی دست‌دادنِ TLS می‌شکند
و مرورگر اصلاً صفحه‌ای نشان نمی‌دهد.  نه هشدار؛ قطعِ کامل.

این با `caddy validate` دیده نمی‌شود (پیکربندی کاملاً معتبر است) و
فقط با اجرای واقعی معلوم شد.  `backend/test/edge.sh` نگهبانش است:
اگر دستورِ tls برداشته شود، لاگِ ACME ظاهر می‌شود و آزمون می‌شکند.

## نقشهٔ نشانی‌ها

| نشانی | کجاست | چه کسی می‌دهدش |
|---|---|---|
| `molido.ir` و `www` | **وب‌سایتِ اصلی** — ۱۹۴.۵.۱۷۸.۱۵۴ | میزبانِ جدا (نه این پروژه) |
| `shop.molido.ir` | فروشگاه | آروان‌کلاود ← ۱۹۴.۵.۱۷۶.۱۴۰ |
| `cafe.molido.ir` | رستوران/کافه | آروان‌کلاود ← ۱۹۴.۵.۱۷۶.۱۴۰ |
| ۱۹۴.۵.۱۷۶.۱۴۰ | همان فروشگاه، مستقیم | راهِ پشتیبان |

⚠️ **`molido.ir` عمداً به سرورِ مولیدو اشاره نمی‌کند.**

این ایراد نیست.  دامنهٔ اصلی وب‌سایتِ شرکت است و جای دیگری میزبانی
می‌شود؛ مولیدو فقط روی زیردامنه‌ها می‌نشیند.  اگر روزی کسی این را
«خرابی» دید و خواست درستش کند، سایتِ اصلی را می‌خواباند.

⚠️ به همین دلیل `ops/set-domain.sh molido.ir` را هرگز اجرا نکنید.
برای چند محصول `ops/set-subdomains.sh` هست.

### آروان‌کلاود جلوی سرور است

و این خبرِ خوبی است: گواهیِ TLS را **لبهٔ آروان** می‌گیرد، نه سرورِ
ما.  سنجیده شد که سرور از بیرونِ ایران در دسترس نیست (۵۲۰)، پس
Let's Encrypt روی خودِ سرور هرگز جواب نمی‌داد؛ با آروان این مشکل
کاملاً برطرف می‌شود.

در پنلِ آروان باید تنظیم شده باشد:

1. مبدأ (origin) = ۱۹۴.۵.۱۷۶.۱۴۰
2. SSL برای هر دو زیردامنه فعال
3. حالتِ اتصال به مبدأ طوری که گواهیِ خودامضای سرور را بپذیرد

⚠️ **و در `.env` سرور: `TRUST_PROXY=2`**

با CDN زنجیره یک حلقه بلندتر می‌شود: مشتری ← آروان ← Caddy ← برنامه.
با مقدارِ `1` برنامه نشانیِ **لبهٔ آروان** را «کاربر» می‌بیند، پس همهٔ
مشتری‌ها یک سطلِ نرخِ مشترک می‌گیرند — اولین کسی که چند بار رمز را
اشتباه بزند، ورودِ همه را می‌بندد.  و هیچ خطایی هم نمی‌دهد، فقط
۴۲۹های بی‌دلیل.  `set-subdomains.sh` با تشخیصِ CDN خودش می‌نویسدش.
